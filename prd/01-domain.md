# 01. ドメイン（GS シリーズと「推しの組み合わせ」）

このアプリが記録・分析する対象は、**ときめきメモリアル Girl's Side シリーズのファンが誰を推しているか**である。
データモデル（[03](./03-data-model.md)）・投票仕様（[04](./04-voting.md)）・分析仕様（[05](./05-analysis.md)）は、
すべて本章のドメイン定義を地盤とする。実装エージェントはまずここを参照すること。

---

## 1. シリーズとキャラクター

- 対象作品は **GS1〜GS4 の 4 シリーズ**。`series` は 1〜4 の整数で表す（`tinyint unsigned`）。
- キャラクターは **全 62 人**（GS1: 18 / GS2: 17 / GS3: 13 / GS4: 13）。
- **攻略対象に限らない**。シリーズ登場人物を広く収録する。
  - 例: GS1・GS3 に登場するバーのマスター **益田義人**（公式サイトのキャラ一覧に載らない）。
  - 例: 各シリーズの女性キャラクター（藤堂竜子・宇賀神みよ 等）、花椿家（吾郎・姫子・カレン・みちる・ひかる）。
  - 収録判断は「ファンが推しとして挙げうるか」であり、恋愛攻略の可否ではない。
- **名称リストの正典は [`server-ts/charactersMaster.ts`](../server-ts/charactersMaster.ts)**。本文書にリストを重複記載しない。
  新規 DB へは `db:seed` が、既存 DB への `reading` 後付けは drizzle マイグレーションが同じデータを使う。

### 1.1 キャラクターの識別と表示

- **キャラクター名（`name`, varchar(20)）がドメイン上の識別子**である。投票も集計も名前で参照する
  （`Votes.character_name` 等は `Characters.name` への FK。→ [03](./03-data-model.md) §3）。
  - 代理キーではなく自然キーを使う。既存データとの互換のため。`ON UPDATE CASCADE` で改名には追随できる。
- **`(series, sort)` が Characters の主キー**であり、これが**公式順**を定める。
  同票時のタイブレーク・凡例順・一覧表示順はすべてこの公式順に従う（[05](./05-analysis.md) §4）。
- `reading`（varchar(40)）はひらがなの読み仮名（姓名の区切りなし）。**キャラ検索専用**で、集計には使わない。
  「きじょうまどか」（姫条まどか）「さくらいこういち」（桜井琥一）「つくし」（尽）など直感に反する読みが多く、
  Wikipedia の各作品記事で検証済み（2026-07 時点）。変更時は必ず出典に当たること。
- 「・」を含む複合名（`クリストファー・ウェザーフィールド`）が存在し、UI 側で 2 段折り返しの特別扱いを受ける
  （[08](./08-frontend.md) §4）。**名前の長さは varchar(20) が上限**で、現行最長がこの名前。

## 2. 「推し」「順位」「組み合わせ」

本アプリの中心概念。ここを取り違えると集計の意味が壊れる。

| 用語 | 定義 |
|---|---|
| **推し（oshi）** | あるユーザーが「好き」と申告したキャラクター。**複数選択可**（1 人〜全キャラ。0 人は投票として認めない → [04](./04-voting.md) §4.1） |
| **順位（level）** | 推しの**上下位置**。小さいほど上位。UI のドラッグ&ドロップの並びをそのまま `level` に落とす |
| **推し set** | あるユーザーの、ある時点での推しの集合（順位付き） |
| **組み合わせ（pair）** | 同一ユーザーの推し set 内に**共起する 2 キャラの順序対** |

### 2.1 順位（level）の仕様

- `level` は「上下位置」を表す非負整数。**小さいほど上位**。
- **現在の UI では 0 始まりの連番**になる。フロントの `favorites` 配列のインデックスをそのまま送るため
  （[`VotingFormClient.tsx`](../next/src/components/VotingFormClient.tsx)）。1 位は `level = 0`。
- **同順位（同じ `level` を持つ複数キャラ）はデータモデル上サポートされる**。
  `LatestVotes` / `Votes` の PK はキャラ名を含むので、同一 `level` の重複を DB は禁じていない。
  `level` を API の独立入力として残すのはこのためである。
  - ✅ **決定（2026-07-10）**: 「1 位が 2 人」を認めたい。**制約は dnd-kit の縦 1 列 UI が全順序を強制していること
    だけ**であり、DB と API はすでに理想形に耐える。同順位を入力できる UI は将来案（[09](./09-roadmap.md) §3）。
  - したがって `level` の**連番性は検証しない**（`0,0,2` の競技順位法も `0,0,1` の密順位法も許す）。
    検証するのは「非負整数・0〜255」まで（[04](./04-voting.md) §4.2）。
- ⚠️ **現状サーバ側に値域検証がない**（zod は `z.number()`、DB は `tinyint unsigned`）。→ 修正対象（[09](./09-roadmap.md) §2.2 C）。
- ⚠️ 開発用 seed（`addTestData.ts`）の `level` は **1 始まり**で、UI が送る値と食い違っている。→ 修正対象（[09](./09-roadmap.md) §2.3 G）。
- `level` は**現状 pair 集計に使われていない**（共起の有無のみを数える。[05](./05-analysis.md) §1）。
  順位を重み付けに使う分析は将来案。

### 2.2 組み合わせ（pair）の定義

あるユーザーの推し set が `{A, B, C}` のとき、そのユーザーが寄与する pair は
`(A,B) (A,C) (B,A) (B,C) (C,A) (C,B)` の **6 個（順序対、自己ペアを除く）**である。

- 集計値 `count(oshi=A, related=B)` は「**A を推す人のうち、B も推している人数**」。
- **対称ではない表示になる**: `count(A,B) == count(B,A)` は常に成り立つ（同じユーザー集合を数えるため）が、
  ページ上では「A 推しの人が同時に推すのは B」という**非対称な読み方**をする。
- 推しが 1 人だけのユーザーは pair を 1 つも作らない（集計に寄与しない）。

## 3. 推しは変わる（時間軸）

- ユーザーは**何度でも投票できる**。「その日最後の投票」がその日の記録になる。
- 記録の粒度は **日（JST）**。同日内の時刻は保持しない（[03](./03-data-model.md) §4）。
- 過去の投票は消えない。`Votes` は**日単位の履歴ログ**であり、推しの変遷を追える。
- 「ある日時点の推し set」は、**その日以前で最も新しい投票日の行**として復元する（as-of 参照）。
  投票しない日が続いても「最後の投票」が有効なままなので、**日付の歯抜けが起きない**。この規則が
  過去日集計（[05](./05-analysis.md) §2）の基礎になる。

## 4. プレイ状態（user state）

- ユーザーは **シリーズごと（GS1〜GS4 の 4 件）に自分のプレイ状況**を申告する。
- 選択肢は `UserStatesMaster` の 3 値（`sort` 昇順）:

| state | sort |
|---|---|
| 未プレイ | 0 |
| 実況視聴 | 1 |
| プレイ済み | 2 |

- 「実況視聴」が独立の値なのは、**プレイせず配信で作品を知っているファンが実在する**ため（README の背景参照）。
- 記録粒度は投票と同じく **日（JST）+ シリーズ**。
- ⚠️ **現状は 4 シリーズすべての値が揃ったときだけ保存される**（[`users.ts`](../server-ts/src/lib/users.ts) `insertUserStatesIfUpdated`）。
  1 つでも欠けると**サイレントに書き込まれない**。**送られた series だけを upsert する部分更新へ変更する**ことが
  決定済み（[04](./04-voting.md) §3.1）。
- プレイ状態は現在 **どの分析にも使われていない**（記録のみ）。「プレイ済みの人の推し傾向」等は将来案（[09](./09-roadmap.md) §3）。

## 5. 日（day）の定義

- **タイムゾーンは常に `Asia/Tokyo`（JST）**。プロセスの `TZ` に依存させない。
- 「今日」= `DateTime.now().setZone('Asia/Tokyo').toISODate()`（luxon）。「昨日」はその `-1 day`。
- DB 上の日付列は `DATE` 型かつ Drizzle の `mode: 'string'`。**`'YYYY-MM-DD'` の文字列としてだけ扱い**、
  ドライバの TZ 解釈を介在させない。
- compose / 本番コンテナは `TZ=Asia/Tokyo`、node-cron も `timezone: 'Asia/Tokyo'` を明示する（二重の保険）。
